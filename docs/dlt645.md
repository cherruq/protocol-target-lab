# DL/T645 software meter workspace

This is a finite autonomous DL/T645-2007 software meter served over a TCP
serial-byte stream. It retains thirteen experimental function classes from
the provided meter reference. It is not a physical meter, RS485/optical port,
1997 implementation, native thirteen-operation SDK or ESAM authentication
system. No serial device, PTY, root privilege or other running protocol is
required. TCP transports the bytes; it does not validate electrical baud,
even parity, a programming button, relay hardware or measured energy.

```json
{"wire_profile":"dlt645-2007-tcp","bind_ip":"0.0.0.0","port":20645,"meter_address":"000000000001","energy_hundredths":12345678,"period_minutes":30,"programming_key_enabled":false,"max_connections":16,"security":{"mode":"reject"}}
```

All nine fields are required. `wire_profile` is a fixed literal, and unrelated
fields/nulls/incorrect types are rejected. This unique shape preserves existing
protocol serialization. IPv4 binding is unicast/wildcard; host port is 1–65535.
Address is exactly twelve ASCII decimal digits, excluding broadcast
999999999999. Energy is an integer 0–99999999 hundredths; period is 1–99 minutes;
concurrent connections are 1–128. These are startup values. Legal requests can
change current address/energy/period without changing the saved configuration.
State survives TCP reconnection and resets on a fresh worker; no persistent
physical metering database is claimed.

Fixed software startup fixtures are baud2400, demand123456 ten-thousandths,
clock2026-01-01T00:00:00 advancing with monotonic elapsed time, and ten permission
levels with three zero test-password bytes each. The software programming-key
boolean is an experimental condition, not a physical button or admin login.
The process never changes the host clock or a physical serial setting.

## Wire and finite operations

The frame is `68 A[6] 68 C L DATA CS 16`, with total length `12+L` and maximum
267 bytes. BCD address bytes are transmitted low pairs first without33H offset.
DI is four little-endian bytes. Every DATA byte uses plus/minus33H modulo256;
CS is the low eight bits of the sum through encoded DATA. Incremental framing
uses L, so DATA16/68/FE does not prematurely terminate a frame. FE wakeup/noise,
fragmentation, coalescing and partial-frame timeout recovery are supported.
1997 two-byte DI and its read function are outside this profile.

| Function | Finite software behavior |
| --- | --- |
| 11 | READ supported energy, period, current address, software baud, time/date and demand DIs; unsupported DI gets an actual error response |
| 13 | AA point-addressed READ_ADDRESS returns actual current address |
| 14 | Simulated programming key and level2/4 test password allow period-only WRITE_DATA with readback |
| 15 | Simulated key permits AA WRITE_ADDRESS; reject broadcast as a meter address |
| 16 | Unicast freeze response; broadcast freeze is silent; software snapshots/counters only |
| 08 | Silent broadcast clock update within five minutes and once per software day |
| 17 | Software baud one-hot value: complete response drains before state commit |
| 18 | Simulated key and permission rules update a software test password |
| 19 / 1A | Demand clear / meter clear with required software permission/key; no inverse energy/demand setter is invented |
| 1C | Finite software relay/alarm/power-hold and deadline; automatic restore uses real five-minute units; the P2=01 status response variant is unsupported |
| 1D | Software output0/1/2 response echo, without physical output proof |
| 03 | Explicit rejection or exact noncryptographic transport fixture |

READ DIs are energy00010000, period04000103, address04000401, baud04000703,
time04000102, datetime0400010C and demand01010000. Replies validate actual
address, response/error/followup flags, DI, data width, BCD, length, CS and end.
Foreign addresses, invalid frames and request response-bits do not mutate
state or receive a generic success ACK. Broadcast procedures retain their
actual silence. A silent window alone does not prove a broadcast state change;
readback or the exact worker's redacted state audit is needed.

The server validates the full command before mutation and serializes each
request transaction, including response drain and pending baud commit. Its
concurrent slot is released before socket EOF, supporting repeated max1
clients. Each connection has its own4096-byte parser, 500ms partial-byte timeout,
30s idle limit and absolute3s drain limit. There is no cumulative frame,
connection-count, duration or log-file expiry. Malformed/overflow connections
are isolated. SIGTERM closes listeners/connections and timer/logger failures
fail the worker for manager supervision. Only internal TCP20645 is published
through Docker bridge; no private observer or serial device is opened.

## Security fixture format and logging

Default is exactly `{"mode":"reject"}`. The alternative is:

```json
{"mode":"fixture","request_di":"07000001","response_di":"070000FF","operator":"00000000","request_hex":"0000000000000000","response_hex":"000000000000000000000000"}
```

Fixture mode requires all five hex fields and no extras. Request DI is one of
07000001/2/3, response DI is070000FF; operator/request/response are exactly4/8/12
bytes. Only exact matching requests receive the configured fixed response.
This proves byte transport, with `crypto_verified:false`; it does not verify
ESAM, MAC, encryption, identity authentication or a real device password.

Stdout JSON records are bounded through a fixed256-entry logger queue. Complete
frame metadata is length/SHA-256 with no raw preview. Unparsed chunks, noise,
partial buffers and authentication payloads are length-only redactions, so a
fragment cannot become a standalone password fingerprint. Startup fixture
material is redacted; credential values and standalone password hashes are
removed from state audit. Password response98 and fixture response83 follow
the same policy. Parsed nonsecret software state/generation is audit evidence,
not cryptographic authentication proof. Docker rotates stdout history.

## Included client and health

```sh
docker run --rm --network host --entrypoint python3 protocol-target-lab/dlt645:0.1.0 \
  -u /opt/protocol-target-lab/client.py --host 127.0.0.1 --port 20645 \
  --method ALL --path meter --config-json "$APPLIED_JSON"
```

The client starts no service and changes no configuration. ALL runs two rounds
of each readonly core case (eight checks), with actual current values:

- READ_ADDRESS: AA request and full current address response.
- READ_DATA: actual current address, energy/period DI, width and BCD validation.
- STREAM: FE prefix, bytewise writes with TCP_NODELAY, coalesced reads/errors,
  encoded DATA16/68/FE, partial timeout then a fresh good request.
- ERROR_RESPONSE: valid unknown DI receives D1/error02, then a good read succeeds.

`--health` performs just AA current-address discovery and an energy read; it
never compares mutable values with startup defaults or treats TCP connect as
success. Clients half-close writes and observe EOF to confirm slot release.
Whole process deadline is30s, each case3s, report512KiB, one stdout JSON, exit0
on complete success or1 on failure. Trace records preserve wire length/hash,
direction and header control while redacting payload material.

WRITE_PERIOD is an explicit optional case requiring the enabled simulated key.
It reads the real current period, changes it, reads it back, then finally
restores and verifies that original current value. Mutation has a1.5s budget,
with recovery bounded by the original3s case/30s process deadline. Lost write
acknowledgements do not imply no mutation; recovery discovers actual state.
Restore failure always fails the case. Only readonly connection admission can
retry during cleanup; no business write is automatically retried.

SECURITY_FIXTURE is another explicit case requiring fixture mode; it compares
the exact response and declares crypto false. Neither optional case belongs
to ALL. Public clients never clear energy/demand, change passwords, synchronize
clock or alter relay state. Full thirteen-operation validation uses disposable
owned fixtures: clear operations have no wire inverse, and passwords/timers/
clock daily guards cannot generally be restored from saved startup values.

## Supply chain and independent validation

The runtime is original stdlib software on the pinned public Python3.12 base,
with no new codec/serial dependency. `scripts/dlt645-fetch-deps.sh` explicitly
prepares the base online; `scripts/dlt645-images.sh` builds offline from the
prepared locked base with an allowlisted context. CPython LICENSE and OS
copyright files remain present. Original code is MIT; image metadata is
MIT AND Python-2.0 with OS components retaining their own licenses.

`scripts/dlt645-assets.sh` exports the runtime, source/tests/recipes, documented
base provenance and manifest. This supports offline wrapper rebuilding from
the prepared base, not a complete operating-system/compiler source bundle.
It does not copy private references or a remote venv and changes no prior
RTP/RTCP source, images or fingerprints.

Optional independent python-dlt6450.1.4 is an MIT **codec subset oracle**.
The original wheel is unchanged; its int-control bug is transparently adapted
with public `load_ctrl(raw[8:9])`. SDK read_frame stops at DATA16, and its DATA
helpers do not implement wrapped33H arithmetic correctly. Therefore it is
used only for supported READ/address/CS vectors with documented limits,
never as a full meter, incremental framer or arbitrary DATA oracle. Complete
modulo/framing/state behavior is checked with independent wire vectors and
actual software state/readback, without physical hardware claims.
